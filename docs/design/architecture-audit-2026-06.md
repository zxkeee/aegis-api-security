# Архитектурный аудит AEGIS — 2026-06

> Разовый снимок состояния архитектуры с находками и планом рефакторинга.
> Контекст: код здоровый (tests race-clean, govulncheck 0, gosec 6×LOW,
> golangci-lint 0). Находки ниже — это **уточнения границ и техдолг**, а не
> пожары. Сортировка по соотношению ценность/риск.

## 1. Что хорошо (сохраняем)

- **Граф зависимостей ацикличный и слоистый.** Циклов нет, слои чёткие:
  ```
  листья:   tenant · logger · config · classify · tlsfp · iam · audit
  L1:       store(→iam,tenant) · proxy(→config,logger) · alert(→logger)
  L2:       forensic(→store) · discovery(→classify,config,tenant)
  L3:       middleware(→audit,classify,config,discovery,iam,store,tenant,tlsfp)
  L4:       api(→ всё выше)
  ```
- **Leaf-дисциплина `tenant` соблюдена** (ADR-001): импортируется всеми, сам не
  импортирует ничего — корректно ломает потенциальные циклы.
- **Размеры здоровые**: крупнейший файл 620 строк (`store/redis.go`), god-файлов
  нет.
- **Две плоскости в одном процессе**, hot-reload через `atomic.Value`,
  fail-closed по контролям, RouteGate для per-route enforcement — добротно.

## 2. Находки

### F1 — «Жирный» интерфейс `middleware.Store` (ISP) · приоритет: ВЫСОКИЙ

`internal/middleware/ports.go` определяет один интерфейс `Store` на ~25 методов
(rate-limit, IP-block, behaviour, challenge, JTI, BOLA, session, forensic…).
Каждый middleware зависит от **всего** интерфейса, хотя использует 2–4 метода.

- **Чем плохо:** нарушение Interface Segregation. Любое изменение `Store` бьёт по
  всем middleware и их фейкам; тест-фейки (`fakes_test.go`) вынуждены
  реализовывать всё; неочевидно, какой контрол что реально трогает.
- **Фикс:** разбить на ролевые интерфейсы — `RateLimiter`, `IPBlocker`,
  `BehaviorStore`, `ChallengeStore`, `RevocationStore`, `AbuseStore`,
  `SessionStore`, `ForensicStore`. Конкретный `*store.Store` продолжает
  удовлетворять всем; каждый middleware принимает только нужный. Риск: низкий
  (чисто декларативно, поведение не меняется).

### F2 — Интерфейс `Store` протекает конкретными типами · приоритет: СРЕДНИЙ

`ports.go` ссылается на `iam.Session` и `store.ForensicEntry` прямо в сигнатурах:
```go
ValidateSession(ctx, token) (iam.Session, bool, error)
PushForensic(ctx, e store.ForensicEntry)
GetForensicLog(ctx, limit) ([]store.ForensicEntry, error)
```
То есть «абстракция» middleware тянет конкретные пакеты `iam` и `store` ради
типов — декаплинг неполный.

- **Чем плохо:** ports.go перестаёт быть границей; middleware жёстко знает форму
  доменных структур чужих пакетов.
- **Фикс:** при разбиении F1 вынести `Session`/`ForensicEntry` в нейтральное
  место или объявить узкие интерфейсы-проекции. Прагматично: это терпимо, т.к.
  `iam` — лист; чинить заодно с F1, не отдельно. Риск: низкий.

### F3 — `store → iam` (персистентность знает домен идентичности) · приоритет: НИЗКИЙ

`store.CreateSession/ValidateSession` оперируют `iam.Session`. Низкоуровневый
Redis-стор связан с доменным типом identity.

- **Чем плохо:** инверсия слоёв — обычно домен (`iam`) владеет своим хранением, а
  не generic-стор импортирует домен. Цикла нет (iam — лист), поэтому не горит.
- **Фикс (опциональный):** перенести session-персистенцию в `iam` (iam получает
  redis-клиент через интерфейс) **или** сериализовать в нейтральный DTO внутри
  `store`. Риск/выгода спорные — возможно, оставить как есть и зафиксировать как
  осознанное решение.

### F4 — `middleware → discovery` конкретный · приоритет: НИЗКИЙ

`middleware` импортирует `discovery` ради `Observation`, `Controls`, `Catalog`.
Часть уже за интерфейсом (`Catalog` в ports.go), часть — конкретная.

- **Чем плохо:** HTTP-слой знает доменную модель discovery напрямую.
- **Фикс:** довести до интерфейса только если будет второй источник discovery
  (out-of-band сенсор, B1). Сейчас — YAGNI, просто зафиксировать.

### F5 — `cmd/gateway/main.go` несёт и composition root, и build-логику цепочки

`main.go` (563 стр.) делает wiring зависимостей **и** содержит
`buildHandlerChain` + хелперы `anyRoute*`. Composition root разрастается.

- **Фикс:** вынести `buildHandlerChain` и `anyRoute*`-хелперы в
  `internal/gateway/chain.go` (или `internal/bootstrap`), оставив в `main.go`
  только запуск/shutdown/wiring. Риск: низкий, улучшает тестируемость цепочки.

## 3. План рефакторинга (последовательность)

1. **F1 + F2 вместе** — разбить `Store` на ролевые интерфейсы, заодно убрать течь
   типов. Это даёт максимум: чище границы, проще фейки, явные зависимости каждого
   контрола. Чисто декларативно, поведение неизменно, покрыто существующими
   тестами. **Делать первым.**
2. **F5** — вынести `buildHandlerChain` из `main.go` в отдельный пакет; добавить
   юнит-тест на сборку цепочки (порядок middleware — load-bearing, сейчас не
   тестируется напрямую).
3. **F3/F4** — зафиксировать как осознанные решения в этом документе ИЛИ чинить,
   только если появится второй потребитель (out-of-band сенсор). Пока — YAGNI.

## 4. Что НЕ трогаем (осознанно)

- Объединение двух плоскостей в один процесс — фича, не баг (простота
  внедрения — единый бинарник).
- Размер пакета `middleware` (22 файла) — нормально для HTTP-слоя; каждый файл —
  один контрол.
- `config` одним файлом (614 стр.) — терпимо; дробить только если перевалит ~1000.
